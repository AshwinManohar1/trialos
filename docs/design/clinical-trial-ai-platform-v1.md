## Problem Statement

Clinical trials fail at alarming rates: 80% don't recruit required patient cohorts on
time, 44% miss recruitment goals entirely. The core workflow — protocol design,
participant recruitment, task execution — is fragmented across CTMS tools (Medidata,
Veeva), spreadsheets, and manual chart review. Existing systems provide data storage
and compliance infrastructure but zero intelligence. The intelligence layer — which
requires reading unstructured documents, reasoning about patient eligibility, and
predicting outcomes — does not exist commercially.

The specific problems in order of severity:
1. Protocol creation is slow and error-prone (eligibility criteria complexity is
   correlated with trial termination)
2. Patient-to-trial matching is done manually (coordinators spend hours per patient)
3. Nobody can predict whether a patient with given characteristics will complete the
   trial or drop out — this is a $50K-$100K/day problem for sponsors

## Demand Evidence

- Existing paying order from a trials company for protocol → task list → roster
  management. Real money. Real relationship. Real trust.
- Research literature: 42% reduction in screening time with LLM-based predictions
  (Jin et al. 2024). LLMs save 165–1,329 hours of reviewing time vs manual evaluation.
- Market: eClinical solutions growing from $10.55B (2025) to $36.42B (2035) at 13%
  CAGR. Trials increasing in volume — making automation more urgent, not less.
- No commercially available solution for patient success simulation exists. All current
  approaches are in academic R&D phase (confirmed by Corbaux et al. 2024).

## Status Quo

A mix of:
- **CTMS tools** (Medidata, Veeva Vault): data storage, compliance, forms. No intelligence.
- **Spreadsheets + email**: small/academic sites. No system at all.
- **Manual chart review**: coordinators read patient records by hand, match against
  printed eligibility criteria. Hours per patient across hundreds of candidates.
- **Protocol drafting**: Word documents, prior protocol templates, medical writer time.

The status quo costs trials companies hours, delays, and failed trials. The tools
exist; the AI layer that makes them intelligent does not.

## Target User & Narrowest Wedge

**Primary buyer**: Trials companies and eClinical software vendors (B2B).
Not hospitals directly. Not pharma sponsors directly.

The existing relationship with a trials company that already ordered adjacent work
(protocol → task list → roster) is the beachhead. They trust the builder, feel the
pain, and are already writing checks for workflow tooling.

**Wedge**: Module 1 — Protocol Intelligence. Turn protocol PDFs into structured,
actionable task lists with role assignments. This is what the existing client already
ordered. No EHR access required. No HIPAA complexity at this stage.

The person who buys this first: a product or engineering lead at a trials software
company who needs to add an "AI" capability to their platform without building it from
scratch. They don't want to replace their CTMS — they want to look smarter.

## Constraints

- Cannot compete with Medidata/Veeva on CTMS infrastructure — enhancement only
- Patient data (EHR access) requires HIPAA BAA, data governance, hospital IT approval —
  comes in Module 2, not Module 1
- Simulation (Module 3) requires historical trial outcome data — needs data partnership
  with CRO or hospital after you have embedded workflow trust
- Regulatory: FDA 21 CFR Part 11, ICH E6(R3) GCP guidelines apply to any system
  touching trial documentation. Need to be aware but not block Module 1.

## Premises

1. Enhancement layer, not full CTMS replacement. Medidata/Veeva are not competitors —
   potential integration partners and distribution channels.
2. Buyer is trials companies and eClinical software vendors (B2B API/embed).
   Not hospitals or pharma sponsors directly.
3. Three capabilities in sequence: protocol creation → recruitment → simulation.
   Don't need to ship all three to generate revenue.
4. The simulation feature (predict patient success likelihood from characteristics)
   is the key long-term differentiator. Nobody ships this commercially.

## Approaches Considered

### Approach A: Protocol Intelligence API Only
Build one thing and stop: LLM reads trial protocols, extracts structure, sells as API.
No roadmap to recruitment or simulation.
- Effort: M | Risk: Low
- Pros: No HIPAA, fastest to ship
- Cons: Smallest moat, leaves the highest-value modules (recruitment, simulation) unbuilt

### Approach B: Modular Platform — Protocol First, Then Expand (Chosen)
Three modules shipped sequentially. Module 1 is identical in scope to Approach A —
the difference is the committed roadmap to Modules 2 and 3. The same API surface
built for Module 1 becomes the foundation for Modules 2 and 3.
- Effort: L | Risk: Med
- Pros: Revenue at each stage, simulation moat achievable, maps to CRO buying patterns
- Cons: Three hard problems sequentially; recruitment (Module 2) competes with funded
  startups (Dyania, BEKHealth)

### Approach C: Simulation-First
Skip Modules 1 and 2, build patient dropout/success prediction directly.
- Effort: XL | Risk: High
- Pros: No commercial competitors, strongest moat
- Cons: Needs historical outcome data before you can sell anything

## Recommended Approach: B — Modular Platform

**Why B over A:** Same Module 1 scope, but commits to the simulation moat. Approach A
leaves the highest-value capability permanently unbuilt.

**Why B over C:** You need data partnerships that only come after being embedded in
real workflows. Protocol → data trust → simulation is the only viable sequence.

### Module 1 — Protocol Intelligence (Ship First)

**Input:** Trial protocol document (PDF or DOCX)

**PDF Parsing approach:**
- Digital PDFs: use PyMuPDF or pdfplumber for text extraction
- Scanned/image PDFs: OCR fallback via Tesseract or AWS Textract
- Protocol length can reach 100-400 pages; chunk by section headers, not page count

**LLM extraction targets (structured output via claude-sonnet-4-6 with tool_use):**
- Study title, phase, therapeutic area, sponsor
- Primary and secondary endpoints
- Inclusion criteria (list of criteria, each tagged with criterion type)
- Exclusion criteria (same)
- Visit schedule (visit name, timing, required procedures per visit)
- Required study roles (PI, co-investigator, coordinator, sponsor monitor, etc.)

**Output schema (JSON):**
```json
{
  "protocol_id": "string",
  "extracted_at": "ISO8601",
  "study": { "title": "string", "phase": "string", "therapeutic_area": "string" },
  "criteria": {
    "inclusion": [{ "id": "I1", "text": "string", "complexity_score": 0-10, "complexity_flags": ["negation", "lab_threshold", "prior_treatment"] }],
    "exclusion": [{ "id": "E1", "text": "string", "complexity_score": 0-10, "complexity_flags": [] }]
  },
  "visits": [{ "name": "string", "day": "number", "procedures": ["string"] }],
  "task_list": [{ "task_id": "string", "description": "string", "assigned_role": "coordinator|PI|sponsor|IRB", "due": "relative_to_enrollment|fixed_date", "visit_ref": "string|null" }],
  "roster_template": [{ "role": "string", "required_count": "number", "qualifications": "string" }],
  "recruitment_risk": { "score": 0-10, "top_risk_criteria": ["I3", "E7"], "rationale": "string" }
}
```

**Eligibility complexity flagging** (the recruitment-risk differentiator):
Each criterion is scored 0-10 by asking the LLM to evaluate:
- Negation complexity ("no prior use of X within 6 months" → harder to verify)
- Lab threshold requirements (specific numeric values needing lab records)
- Time-window constraints (prior treatment within N months)
- Subjective assessments ("clinically significant" without definition)
Score aggregated to trial-level recruitment_risk score. Basis: Reinisch et al. 2024
showed eligibility criteria complexity is correlated with trial termination.

**Error handling:**
- Unparseable PDF → return `{ "error": "parse_failed", "reason": "string" }`
- LLM extraction confidence below threshold → flag fields with `"confidence": "low"`
- Partial extraction (some sections missing) → return what was extracted with
  `"extraction_status": "partial"`, log which sections were not found

**API surface (Module 1):**
```
POST /v1/protocol/extract
  Body: { "file_url": "string" } or multipart file upload
  Returns: extraction job_id

GET /v1/protocol/{job_id}/status
  Returns: { "status": "pending|processing|complete|failed", "result_url": "string" }

GET /v1/protocol/{job_id}/result
  Returns: full JSON schema above

POST /v1/protocol/{job_id}/webhook
  Register a callback URL for async completion notification
```

**Pricing:** $200-$500 per protocol processed (defensible — a protocol takes a
coordinator 8-20 hours to manually parse; at $50/hr that's $400-$1000 in labor saved).

**8-week milestones:**
- Week 1-2: PDF parser + OCR fallback + Claude extraction prompt (schema above)
- Week 3-4: API endpoints, webhook delivery, error handling
- Week 5-6: Complexity scoring, recruitment_risk field, output validation
- Week 7-8: Pilot with existing client, iterate on schema based on feedback

**"Traction" definition for gating Module 2:** Two paying B2B customers using Module 1
in production, with measurable time-saving feedback from at least one.

---

### Module 2 — Participant Recruitment (After Module 1 Traction)

- Patient-trial matching: given structured patient characteristics, predict eligibility
- Criterion-level LLM predictions with rationale (explainable)
- Requires: HIPAA BAA, EHR integration (FHIR R4 preferred)
- Sell as API to trials companies who handle the hospital relationship
- Stack additions: vector store for protocol criteria, FHIR client, RAG over
  ClinicalTrials.gov (this is where ClinicalTrials.gov integration belongs, not Module 1)

---

### Module 3 — Patient Simulation (After Data Partnerships)

- Input: Patient characteristic profile (age, comorbidities, prior meds, demographics)
- Output: Predicted trial completion likelihood + dropout risk factors + historical
  cohort comparables
- Requires: Historical trial outcome data (CRO data partnership or MIMIC/academic datasets)
- This is the moat. A single prevented dropout at $50K/trial-day is a clear ROI case.
- Gate: Do not sell this until dropout prediction accuracy exceeds 70% on held-out data.

## Open Questions

1. What EHR format does the existing trials company's clients use? FHIR compliance
   determines Module 2 integration complexity.
2. Does the existing client have historical trial outcome data they'd share for
   Module 3 validation? This is the critical unlock.
3. Regulatory posture: Will you pursue FDA SaMD (Software as Medical Device)
   classification for simulation output, or position as "decision support only"?
4. Pricing model: Per-API-call, per-seat, or per-trial? Per-trial aligns incentives
   best (you win when they recruit successfully).

## Success Criteria

- Module 1: Existing client goes live within 8 weeks. Second B2B customer signs within
  3 months of Module 1 shipping.
- Module 2: 30%+ reduction in manual screening time for pilot site (measurable in
  coordinator hours).
- Module 3: Dropout prediction accuracy > 70% on held-out historical data before
  selling to any sponsor.

## Distribution Plan

B2B API first. No direct-to-hospital sales motion initially.

- **Module 1**: REST API + webhook integration. Trials company embeds in their existing
  CTMS workflow. Pricing: per-protocol-processed ($200–$500/protocol is defensible
  given hours saved).
- **Module 2**: White-label API that trials software vendors embed. They handle the
  hospital relationship; you handle the intelligence.
- **Module 3**: Enterprise deal with CRO or pharma sponsor. Requires data sharing
  agreement. Pricing: annual contract tied to trial volume.

No consumer play. No direct EHR marketplace (App Orchard, Epic App Market) until
you have clinical validation data.

## Dependencies

- Claude API access (Anthropic) — claude-sonnet-4-6 for reasoning tasks (Module 1, 2, 3)
- PyMuPDF or pdfplumber — PDF text extraction (Module 1)
- Tesseract or AWS Textract — OCR fallback for scanned protocols (Module 1)
- ClinicalTrials.gov API (free, public) — trial registry data (Module 2+)
- FHIR R4 — EHR integration standard (Module 2+)
- Historical trial outcome dataset — MIMIC, CRO partnership, or academic data (Module 3 blocker)
- Legal: HIPAA BAA with any customer handling patient data (Module 2+)
- Regulatory awareness: FDA 21 CFR Part 11 (electronic records), ICH E6(R3) GCP (Module 2+)

## The Assignment

**Before you write a single line of code:** Go back to the trials company that placed
the order. Ask them one question: *"If I could read the protocol document and
automatically flag which eligibility criteria are most likely to cause recruitment
problems — would that be worth paying for separately?"*

Their answer determines whether Module 1 is a product or just a project. If yes, you
have a second use case with the same buyer. If no, find out what they would pay for —
the answer will reshape the output schema.
